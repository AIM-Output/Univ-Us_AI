# f9-r0 를 GGUF 로 바꿔 CPU 만으로 돌려 본 기록 (2026-11-22)

가이드 10장의 길(합치기 → GGUF → llama.cpp)이 실제로 되는지, 그래픽카드 없는 PC 에서 얼마나 걸리는지 한 번 끝까지 돌려 본 기록입니다.
그때 있던 어댑터가 f9-r0 뿐이라 **f9-r0 로 쟀습니다.** f9-r1 로는 아직 하지 않았습니다. 모델 크기와 프롬프트 길이가 같아 속도는 비슷할 것으로 보지만, 잰 것은 아닙니다.

## 방법

| 단계 | 무엇 | 결과 |
|---|---|---|
| 합치기 | 어댑터를 베이스 가중치에 더함 — `W + (alpha / r) · B @ A`, 대상 252개. fp32 로 계산해 fp16 으로 저장 | 4비트(nf4)로 다시 줄이지 않았습니다(가이드 10장 1번) |
| 변환 | llama.cpp `convert_hf_to_gguf.py … --outtype f16` | 15초 · 7.5GB |
| 양자화 | `llama-quantize … Q4_K_M` | 46초 · **2.33GB** |
| 실행 | llama.cpp 공식 CPU 전용 빌드 `b12359` 의 `llama-server` (Windows x64) | — |

- 장비: 하람 데스크톱의 CPU 만 사용 (i5-14400F · DDR5 32GB). 그래픽카드는 쓰지 않았습니다.
- 입력: eval 문장. system 안내 + 도구 11개 정의 때문에 **입력이 약 2,020 토큰**입니다.
- 합치기 스크립트는 그때의 임시 폴더에만 있었고 지금은 남아 있지 않습니다. 위 식대로 다시 쓰면 됩니다.

## 결과 — 요청 하나에 걸린 시간 (`bench_cpu.json`)

| 스레드 | 처음 보는 입력 | 같은 분 안의 다음 요청 | 분이 바뀐 뒤 첫 요청 | 입력 읽기 | 출력 |
|---:|---:|---:|---:|---:|---:|
| 4 | 35.0~38.9초 (2회) | 2.5~5.6초 | 38.7초 | 59~61 토큰/초 | 8.7~9.3 토큰/초 |
| 6 | 27.4~30.7초 (2회) | 2.3~5.1초 | 30.7초 | 77~78 토큰/초 | 9.8~10.0 토큰/초 |
| 8 | 23.8~29.8초 (16회 · 중앙 26.0초) | 1.8~4.0초 | 26.4초 | 86~90 토큰/초 | 10.9~12.6 토큰/초 |

- **시간의 대부분은 입력을 읽는 데 듭니다.** 2,020 토큰을 읽는 데 22~34초, 답 17~43 토큰을 쓰는 데 1~5초입니다.
- **같은 분 안에서는 빠릅니다.** 앞의 1,998 토큰을 다시 읽지 않고 재사용하기 때문입니다.
- **분이 바뀌면 다시 느려집니다.** system 안내 맨 앞의 날짜·시각 줄이 달라져서 재사용이 25 토큰에서 끊깁니다.
- 서버 메모리는 약 5.2GB 였습니다. 요청을 16개 이어서 보낸 8스레드 측정에서는 9.2GB 까지 늘었습니다(프롬프트 캐시가 쌓인 것으로 보이지만 확인하지 않았습니다).

## 답이 같은가

같은 16문장을 GGUF(Q4_K_M · llama.cpp)와 원래 방식(4비트 · transformers)으로 답하게 해 비교했습니다.

- 16문장 중 **15문장이 같은 도구·인자**였습니다. 다른 1문장은 공강 배치 문장입니다.
- 정답과 맞은 수는 GGUF 14 · 원래 방식 13 입니다.
- llama.cpp 가 센 입력 토큰 수가 transformers 와 정확히 같았습니다 — 프롬프트가 같은 모양으로 들어간다는 뜻입니다.

16문장은 적습니다. 가이드 10장 3번의 재채점(eval · real_dev 전체)은 아직 하지 않았습니다.
