# f9-r1-date — f9-r1 에 이어서 날짜 보강 학습 (채택하지 않음)

f9-r1 의 날짜 약점([`../date_probe/`](../date_probe/))을 학습으로 고쳐 보려던 run 입니다. **고쳐지지 않았고 eval 이 나빠져서 채택하지 않았습니다.** 최고는 그대로 f9-r1 입니다.
날짜는 그 뒤 학습이 아니라 규칙으로 풀었습니다([`../date_rule/`](../date_rule/)).

| 항목 | 값 |
|---|---|
| 날짜 · 장소 | 2026-11-23 14:11 ~ 17:18 · 하람 데스크톱 (RTX 5060 8GB) |
| 바꾼 것 | ① 새 어댑터가 아니라 **f9-r1 어댑터에서 시작** ② 데이터 3,000행 = 날짜 보강 1,000 + 기존 학습 행 2,000 |
| 데이터 만들기 | `python src/prepare_f9_dates.py --n 1000 --seed 23 --mix 2000 --mix_text 500 --mix_out data/f9-r1-date` |
| 학습 명령 | `RUN_NAME=f9-r1-date DATA_DIR=data/f9-r1-date bash train.sh --low_vram 1 --init_adapter outputs/f9-r1/adapter` |
| 평가 명령 | `eval.py --adapter outputs/f9-r1-date/adapter` 로 eval 358턴과 날짜 진단 180문장 (학습 전 모델은 f9-r1 때와 같아 다시 채점하지 않음) |
| 설정 | `config.env` 그대로 — LR 2e-4 · 1 epoch · r=16 |
| 데이터 지문 | `data/f9-r1-date/train.jsonl` 3,000행 `eaef20d494b1` · `data/f9/extra_dates.jsonl` 1,000행 `9d3b3ecb8856` (`data_sha256.txt`) |
| 시작 어댑터 | f9-r1 — sha256 앞 12자리 `9ce7a5eccf74` (`run.json` 의 `init_adapter`) |
| 어댑터 | Release `f9-r1-date` — 기록용입니다. 쓰지 않습니다 |

> **가이드 3-7 의 규칙 8("본 학습은 머지된 코드·데이터로만")을 지키지 못한 run 입니다.** 학습할 때 `src/train.py` 의 `--init_adapter` 와 `src/prepare_f9_dates.py` 는 커밋 전이었습니다. 이 PR 에 올린 두 파일은 그때 쓴 파일과 sha256 이 같습니다(`be56fce9a11d` · `72101f4d501d`).

> **같은 데이터를 다시 만들려면** 실제 문장이 320개이던 때의 `data_src/real` 을 줘야 합니다 — 생성기가 실제 문장과 겹치는 날짜 상황을 피하기 때문입니다. `--real <커밋 3e4031c 의 data_src/real>` 을 주면 위 지문과 같은 파일이 나오는 것을 2026-11-27 에 확인했습니다. 지금(380개) 그대로 돌리면 다른 파일(`1715b5b2fcf4`)이 나옵니다.

## 결과

| 시험 | f9-r1 | f9-r1-date | 변화 |
|---|---:|---:|---|
| eval 턴 정확도 (358턴) | 351 (98.0%) | 346 (96.6%) | **−1.4%p** · 고쳐짐 1 · 나빠짐 6 |
| eval 도구 선택 (293턴) | 293 | 293 | 그대로 |
| eval 거절 (65턴) | 65 | 65 | 그대로 |
| eval 과잉 거절 | 0 | 0 | 그대로 |
| 날짜 진단 — 말일·1일 (108문장) | 72 (66.7%) | 68 (63.0%) | 나빠짐 |
| 날짜 진단 — 그 밖 (72문장) | 67 (93.1%) | 63 (87.5%) | 나빠짐 |

**판정: 채택하지 않음.** 가이드 9장 판정 규칙 1은 eval 턴 정확도가 1%p 넘게 떨어지면 새 최고가 될 수 없다고 정합니다.

eval 에서 달라진 턴 (`compare_with_r1.txt`):

- **고쳐진 1턴** — 10-22 기준 "9일 뒤" 를 10-31 로 맞혔습니다. 이 날짜 상황은 학습 데이터에서 일부러 뺐으므로 외운 것은 아닙니다.
- **나빠진 날짜 4턴** — 11-27 기준 "4일 뒤" 와 11-29 기준 "2일 뒤" 를 달력에 없는 11월 31일로, 12-07(월) 기준 "이번 주 토요일" 을 하루 앞으로, 12-06 기준 "다음 달 16일" 을 같은 달로 답했습니다.
- **나빠진 수정 2턴** — 시각만 바꾸는 요청인데 바뀌지 않은 제목까지 `patch` 에 넣었습니다. 학습 데이터에 그런 행은 없습니다.
- **그대로 틀린 6턴** — 공강 배치 5턴과, 10-25(일) 기준 "다음 주 토요일" 1턴(f9-r1 은 11-07, 이번에는 11-01 로 답함. 정답 10-31).

날짜 진단에서는 180문장 중 49문장의 정답 여부가 바뀌었습니다(고쳐짐 21 · 나빠짐 28). 오류의 모양도 바뀌었습니다 — 정답이 31일인 문장에서 한 주 뒤로 답하는 오류는 6 → 1 로 줄고, 다음 달 1일로 답하는 오류가 12 → 24 로 늘었습니다.

## 학습

- 440 step · 평균 loss 0.0096 · 3시간 7분 (step 하나에 25.5초) · 행 3,000 · 쌍 3,520 · 버린 행 0
- loss 는 처음 40 step 평균 0.012 → 81~120 step 0.015 → 마지막 40 step 0.004 입니다(`loss_summary.txt`). f9-r1 에서 시작했기 때문에 처음부터 낮습니다(새 어댑터로 시작한 f9-r1 은 첫 5 step 평균 1.4).
- **가중치는 f9-r1 에서 많이 움직였습니다**(`adapter_diff.txt`). 텐서 504개 각각의 상대 차이가 중앙값 41%(최소 6% · 최대 98%)이고, `lora_B` 전체 크기가 15.9 → 19.1 로 커졌습니다.
- 학습 가능한 파라미터 수는 f9-r1 과 같습니다(33,030,144).

## 데이터

- **날짜 보강 1,000행** (`data_extra_dates.README.md`) — 말투와 정답 계산은 v2 생성기 그대로이고, 기준시각만 정답이 말일·1일에 떨어지게 골랐습니다. "N일 뒤" 263행 · "다음 주 X요일" 273행. 정답이 1일 488 · 말일 468.
- **기존 학습 행 2,000행** (`data_mix.README.md`) — 거절을 잊지 않게 섞었습니다. 글로 답하는 행(거절·인사)을 500행으로 맞춰 전체 비율을 원래 데이터와 같게(16.7%) 했습니다.
- eval · 실제 문장 · 날짜 진단과 **같은 문장**뿐 아니라 **같은 날짜 상황**(같은 기준일 → 같은 정답 날짜)도 뺐습니다. 시험이 학습에서 본 적 없는 계산을 재게 하려는 것입니다. 이 때문에 "N일 뒤" 상황의 28%, "다음 주 X요일" 상황의 37% 가 학습에서 빠졌습니다.
- 그 결과 이번 학습 3,000행에서는 정답 날짜의 59% 가 28~31일이나 1일입니다. 원래 학습 데이터는 17% 입니다.

## 왜 안 됐는가 — 확인한 것과 추정

확인한 것:

- 보강 데이터의 정답은 맞습니다. 1,000행 모두 문장에서 다시 읽은 날짜·시각이 정답과 같습니다.
- 거절과 도구 선택은 잊지 않았습니다. 나빠진 것은 날짜 계산과 수정 인자입니다.
- 가중치가 "가볍게 덧칠" 수준을 넘게 움직였습니다.

추정 (확정이 아닙니다):

- 경계 날짜 문장 1,000개를 한 번씩 본 것으로는 달 길이 계산을 배우지 못했고, 틀리는 방식만 바뀐 것으로 보입니다.
- 학습에 쓴 날짜 행 자체를 이 어댑터가 맞히는지는 재지 않았습니다. 그래서 "못 배웠다" 와 "외웠지만 새 날짜에 못 쓴다" 를 가르지 못합니다.
- LR 을 낮추거나 epoch 를 늘린 재시도는 하지 않았습니다.
